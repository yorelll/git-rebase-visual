# 🔴 P0 — 新引入的风险 / 承诺未兑现

## 1️⃣ 【新风险】过滤 or 折叠状态下的拖拽重排，语义未定义

这是本轮新增「搜索框」和「锁定分组折叠」后**必然出现的安全漏洞**，优先级最高。

**场景 A：过滤中拖拽**
```
搜索 "isp"  →  列表只剩 3 行（原本 12 个 commit）
用户把第 3 行拖到第 1 行
问题：这 3 个 commit 在真实历史里并不相邻，中间隔着 5 个 commit
     → 生成的 todo 到底怎么排？用户预期完全无法验证
```

**场景 B：拖到折叠分组上**
```
▼ 🔒 8 个连续锁定 commit    ← 折叠时，把一个 commit 拖到这一行上
问题：是插到组前？组后？还是组内第 4 位？无从判断
```

必须明确处理（建议）：

| 状态           | 建议行为                                                                                                                      |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 搜索框非空     | **禁用拖拽**（grip 变灰 + tooltip：`过滤中无法重排，请先清空搜索`）；或过滤时显示"上下文行"（灰显未匹配行，保持真实相邻关系） |
| 拖到折叠分组   | 定义为 **插入到整组之后**，并在插入线旁显示文字 `插入到 8 个锁定 commit 之后`                                                 |
| 拖动跨越折叠组 | 自动展开该组（`dragover` 400ms 后 auto-expand），避免"盲拖"                                                                   |
| 任意重排落地前 | 显示确认摘要：`将 f5a8777 移动到 31fe2ce 之后，影响 8 个 commit 的 hash`                                                      |

## 2️⃣ 【承诺未兑现】edit 停靠时仍没有「追加到此 commit (amend)」入口

截图 2 横幅明确写着：

> 「可修改代码或提交新改动后继续。」

但下方「未提交的改动」区只有两个按钮：
- `生成 message 并提交暂存区` → 会**新建一个 commit**
- `仅生成 message（不提交）`

❌ **缺最关键的那个**：edit 停靠最常见的用途就是"改一下这个 commit 本身"，即 `git commit --amend`。目前用户必须切到终端。

建议停靠期间的未提交区改为：

```
在此 commit 上的改动：1 个暂存 · 15 个工作区
┌────────────────────────────────────────────┐
│ [追加到 6c710eb2 (amend)]   ← 主按钮，停靠时的默认动作
│ ▼ 更多                                      │
│    生成 message 并新建 commit               │
│    仅生成 message（不提交）                 │
│    提交全部改动（git add -A）⚠              │
└────────────────────────────────────────────┘
```

- 🔹 amend 时若原 message 需要改，直接复用 Compose 面板（预填原 message）
- 🔹 amend 按钮标签带上目标 hash，避免"我 amend 的是哪个"的疑虑

## 3️⃣ 【仍缺】冲突态 UI 完全没有

两轮都提到，仍未见落地。截图 2 是 edit 停靠（安全态），但**冲突态**（真正需要帮助的时刻）依然缺：

- ❌ 无 `Skip`（`git rebase --skip`）—— 冲突场景的常用出口
- ❌ 无冲突文件列表 / 数量
- ❌ `Continue` 在冲突未解决时**仍可点**（应禁用 + tooltip 说明还剩几个文件）
- ❌ 横幅配色未区分：edit 停靠已改蓝 ✅，但冲突态应为**红色**（`editorError`）

建议冲突态横幅：

```
┌──────────────────────────────────────────────┐
│ ⚠ 变基冲突 · 步骤 4 / 12                     │
│    6c710eb2 "feat(cif): update cif regs"     │
│                                              │
│  ⚠ 2 个文件冲突未解决（点击展开）             │
│    · drivers/media/rts_camera_isp.c          │
│    · drivers/media/rts_camera_pwm_regs.h     │
│                                              │
│  [Continue]🚫  [Skip]        [Abort]         │
│   └ tooltip: 还有 2 个文件未 git add          │
└──────────────────────────────────────────────┘
```

## 4️⃣ 【新风险】Compose Tab 缺 commit 上下文 + 无未保存保护

截图 3 中：

- ❌ Tab 标题：`AI compose commit message`；面板标题：`Compose commit message`
- ❌ **完全看不出正在编辑哪个 commit**（没有 hash、没有 subject）
- ❌ 可以同时开多个 compose tab → **极易改错 commit**
- ❌ 关闭 tab 无二次确认 → 写了半天的 message 静默丢失

必须补：

```
Tab 标题：  reword 6c710eb2 · feat(cif): update cif regs
面板头部：  ✏ 编辑 message  ·  6c710eb2  ·  feat(cif): update cif regs
                                             [在列表中定位 ↗]
```

- 🔹 同一 commit 只允许一个 compose tab（重复调用则聚焦已有 tab）
- 🔹 内容被修改后 tab 标记 `●` dirty 点，关闭时提示 `是否放弃对 message 的修改？`
- 🔹 若在 compose 打开期间目标 commit 因其他操作被改写 → tab 顶部黄条警告 `该 commit 已变化（6c710eb2 → a1b2c3d4），建议重新打开`

# 🟠 P1 — 明显影响体验

## 5️⃣ 【本轮回归】「待重放」提示逐行重复，行高从 2 行涨到 3 行

截图 2 中 8 个待重放 commit，**每一行都挂着一句一样的话**：

```
change(isp): bypass clk rate set and add reg hack
f5a8777c*（待应用）· lawrence_lv · 2026-08-13
待重放：Continue 后 hash 将变化           ← 8 行完全相同的文字
```

- ❌ 8 行 × 1 行冗余文字 = 白白吃掉 8 行高度
- ❌ 每行 3 行高，列表长度暴涨，滚动成本明显上升
- ❌ 同时出现 **`（待应用）`** 和 **`待重放`** 两种说法，术语不统一

建议改为**一条分隔线 + 区块淡化**（上轮原意）：

```
  ⋮ Ⓛ feat(cif): update cif regs        [⏸ 停在此]
      6c710eb2 · lawrence_lv · 2026-07-30
─── ↓ 以下 8 个 commit 待重放，Continue 后 hash 将变化 ───
  ⋮ Ⓛ change(cif): split vc shift for source ctrl      ← 整段 opacity: .55
      31fe2ce9* · lawrence_lv · 2026-07-30
  ⋮ Ⓛ change(isp): bypass clk rate set and add reg hack 🔒
      f5a8777c* · lawrence_lv · 2026-08-13
```

- 🔹 hash 后 `*` 保留（轻量标记），tooltip 说明含义
- 🔹 术语统一用 **「待重放」**（对应 git 的 replay 概念），删除「待应用」(文档中解释待重放的含义)

## 6️⃣ 锁定分组

文案有问题：

| 现状                                    | 问题                                             | 建议                                                                 |
| --------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------- |
| `8 个连续锁定 commit（可作为重排目标）` | 「可作为重排目标」语义费解，且强调了一个次要能力 | `🔒 8 个锁定 commit · 不会被推送`                                     |
| 无作者聚合                              | 看不出是谁的提交，而这正是锁定的核心信息         | `Ⓛ×5 Ⓢ×2 Ⓨ×1` 或 `lawrence_lv ×5 · sally_peng ×2 · yucheng_xiang ×1` |

```
▶ 🔒 8  · not push · Ⓛ×5 Ⓢ×2 Ⓨ×1 · f5a8777c…f13a26c8
```

- 🔹 **默认折叠**（`gitRebaseVisual.collapseLockedRuns` 默认 on），记住用户手动展开状态
- 🔹 分组外框边线偏重，与行的左侧橙条形成双层框；建议去掉外框，只保留**贯通的橙色左条**
