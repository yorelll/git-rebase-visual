## Git Rebase Visual 0.8.0

用于 VS Code 的可视化交互式 Git rebase 扩展：在侧边栏中安全地重排、编辑、锁定和推送 commit，并提供工作区恢复、只读 Diff、AI commit message、stash 与受控 Undo。

> 来源：Git tag `v0.8.0` · GitHub Actions 自动构建 · CI 将执行 `npm run test:release`、VSIX 内容校验与版本记录校验。

### ✨ 变化（0.8.0）

- **详情与操作重新回到侧栏**：悬停 commit 约 0.4 秒后，作者、时间、`hash + 变更统计` 和完整 message 显示在**侧栏内该行旁边**的浮动浮层中，可直接复制 message 或打开变更 Diff，指针移入浮层可继续阅读，移出后自动关闭。右击 commit 或按 `Shift+F10` / Menu 键在**侧栏内**打开操作菜单，不再打开编辑器区面板；多选 ≥2 个 commit 时，菜单直接提供批量锁定、批量删除与连续区间生成 Diff。点击编辑器或窗口变化仍会关闭菜单。
- **写操作不再无声卡住**：写锁从裸布尔值改为带 owner 身份的操作锁。被拒绝时会说明正在执行的操作、来源（侧栏 / 命令）与已耗时，例如 `正在执行 “变基重排” (reorder, webview, 12s)；请等待完成，或点击“强制解除”。`
- **看门狗与安全恢复**：操作超过 90 秒仍未结束会写入一行 `mutation-stuck` 诊断并弹出带 **强制解除并刷新** 的警告。强制解除会重新读取 Git 的 rebase 标记、冲突文件与 commit 列表后再刷新，不依赖内存状态，因此在终端里已经结束或手动恢复的仓库是安全的；owner 已结束但释放丢失时，下一条消息会自动回收，不会永久 busy。
- **文件日志**：一次扩展会话一个带时间戳的日志文件，默认位于 `<系统临时目录>/log/git-rebase-visual-<version>/`（Windows 通常为 `%TEMP%\log\git-rebase-visual-0.8.0\`），按大小轮转并保留最近 10 个会话文件。可用 **Git Rebase: Open Logs**（`gitRebaseVisual.openLogs`）直接打开该目录。日志文件与 **Output → Git Rebase Visual** 的第一行是会话头，记录扩展版本、扩展安装路径、VS Code 版本、扩展宿主 pid 与操作系统，用于确认当前运行的到底是哪个构建。
- **插件永不自动删除 stash**：恢复全程只用 `git stash apply`（含 `--index`），自动路径上没有任何 `git stash pop` / `git stash drop` / `git stash clear`；`stashDropBySha`、`stashPopBySha`、`dropConfirmed`、`dropListedStash` 等“自动删除”实现已整体删除，`git stash pop` 只存在于用户显式点击 **Pop** 的命令里。记录只有在内容被**正面确认**已在工作区/暂存区/HEAD 中时才清除；确认不了（仅模式变化、revert 形状、目录重命名、同字节巧合、探测失败）就同时保留记录、横幅与 stash。误判的最坏结果是“多留一个 stash”，永远不会是“唯一副本被删掉”。
- **待恢复改动对账与 Reset Extension State**：启动/刷新时以真实 Git 状态（rebase 是否进行、stash 是否仍列出、stash 内容是否已在 index/worktree、`targetHash` 是否仍是 HEAD 祖先）对账遗留的追加/自动 stash 记录。**对账失败即保守**：任何探测（读 `^1`/`^2`/`^3` 对象或 `^3` 树、非零退出的 `git diff`、失败的 `git stash list`）出错时，对应部分记为“未知”而非“已存在/已恢复”，整轮判定为 `pending`，记录与 stash 原样保留并写明原因。追加路径不再只看 `targetHash` 是否为祖先，还会用 `git ls-tree` 逐路径比对快照 `^2` 与 `HEAD` 的 **mode + object**，任何一项读不到或不同都保留记录。无法自动恢复时侧栏显示可关闭的“待恢复的改动”横幅，commit 列表照常渲染；横幅按 `(stash sha, 原因)` 的 key 渲染，关闭后在下一次轮询中不会重新出现，只有出现**不同** key 才再次提示。横幅与 reset 报告都会列出可直接执行的恢复命令：`git stash apply --index <name>`、`git stash apply <name>`、以及确认不再需要后才由**用户自己**执行的 `git stash drop <name>`。恢复按记录单飞，轮询/事件/读取消息重叠时只执行一次，并整轮获取与写操作相同的 mutation lock：写操作持锁时本轮直接跳过、等下一次空闲轮询，绝不在锁外执行 Git 写操作；对账不在渲染路径上，commit 列表先渲染，对账异步进行并在持续失败时指数退避（最长 30 秒）。新增命令 **Git Rebase: Reset Extension State**（`gitRebaseVisual.resetState`）：先做同样的 Git 对账，只清理孤儿状态记录，绝不删除仍保存未提交内容的 stash，并报告清理/保留内容（含保留 stash 的可执行命令）与日志目录。

### 🐛 修复（0.8.0）

- **“上一个操作尚未完成，请稍候。”永久卡住**：`runGit` 之前只在子进程 `close` 时结算，而 Git hook、rebase editor 或其它后台孙进程会继承 stdout/stderr 管道，使 `close` 永不触发；同时 120s 超时的 `child.kill()` 只杀直接子进程。现在以子进程 `exit` 为准（输出排空即结算，否则 50ms 宽限后结算），超时/取消在固定宽限后只结算一次，并用 `taskkill /T /F`（Windows）或进程组信号（POSIX）**尝试**回收进程树——`taskkill` 只能沿树根向下枚举，已脱离或期间新建的孙进程可能存活，那只是进程泄漏，不再阻塞结算、不再泄漏监听器/定时器/未结束的 Promise，也不会触发 `EPERM`。
- **忙碌提示无法说明原因**：拒绝消息现在命名具体操作、来源与耗时，而不是笼统的一句“请稍候”。
- **强制解除可能读到过期状态**：恢复路径先重新读取 Git 状态再刷新，不假设内存中的 rebase/冲突信息仍然有效。
- **“追加事务未完成”“卸载重装仍报”**：`refresh()` 过去在自动恢复失败时直接 `return`，整张 commit 列表被一条过期记录吞掉；同时它只相信持久化标记，从不检查 stash 内容是否其实已经恢复。现在先与 Git 对账再渲染：记录对应的内容已在 index/worktree 中（例如用户手动执行过 `git stash apply --index`，或 `stash apply` 其实已成功但未丢弃 stash）会被判定为已恢复并静默清除；rebase 已被中止、`targetHash` 仍是祖先时，快照按“可恢复”而不是“可丢弃”处理。自动恢复现在只做 `apply`（旧实现会在成功后 `pop`/`drop`，冲突的 `pop` 还会先清掉记录却不告警）——记录只在内容确认已恢复时清除，stash 条目一律保留。
- **重复告警**：1.5 秒轮询过去会让同一条待恢复警告反复弹出通知；现在按 `(stash sha, 原因)` 去重，重复只写文件日志，界面保留一条可关闭的横幅。
- **“关闭提示”按钮无效**：横幅过去每次刷新都从 `recoveryNotice` 重新渲染，关闭后的 `refresh()` 又把同一条横幅画回来。现在横幅文本随去重状态一起持久化，渲染只读取当前 key；关闭后保持清除，直到出现不同的 `(stash sha, 原因)`。
- **探测失败被当成“已恢复”**：`changedPaths()` 在非零退出时返回空数组、`treeBlobs()` 在失败时返回 `undefined`，而 index/worktree/untracked 三部分默认就是 `"present"`，于是任何探测失败都会让 `complete === true` 并触发 `git stash drop`，可能删掉唯一一份未跟踪文件。现在三部分默认 `"unknown"`，只有探测成功才提升状态；同时**自动 drop 已被整体删除**，探测结论只用来决定“是否清记录”，不再决定“是否删 stash”。
- **失败的 `git stash list` 被当作“stash 已消失”**：`stashShas()` 过去在非零退出时返回 `[]`，而 Git 在 reflog 损坏时会以 **exit 0 + 空输出** 返回，`refs/stash` 却仍指向真实 stash；两种情况都会被当成内容已不存在。现在非零退出，或“列表为空但 `refs/stash` 指向列表外的 sha”都返回 `undefined`（未知），保留记录、写入 Git 错误并只告警，不声称内容已恢复。
- **仅凭祖先关系判定“已并入 amend”**：`targetHash` 仍是 HEAD 祖先并不代表快照内容在 HEAD 里（`git reset --hard` 后祖先检查失败、HEAD 也缺文件，记录却被静默清除）。现在会逐路径用 `git ls-tree` 验证快照 `^2` 与 `HEAD` 的 **mode + object** 是否真的一致，不一致或读不到就保留记录。
- **真正完成的追加可能永远不结算**：amend 之后若同一文件在后续 commit 中又被修改（例如追加改第 2 行、后续 commit 改第 18 行），最终 `HEAD:path` 与快照的 blob 本就不相等，旧逻辑会一直报“无法确认快照已进入 HEAD”。判定改为 `git ls-tree` 逐路径 mode + object 比对；仍不一致时不再猜“是否曾出现过”，而是保留记录并给出可执行命令——**永久 pending 现在是可接受、有出口的状态**，代价只是多留一个 stash，而不再有删错的风险。
- **索引匹配就清除记录，可能丢掉只存在于 stash 的未跟踪内容**：追加后的对账原先把 `contentPresent || index === "present"` 当作完成，于是“索引已匹配、工作区未跟踪文件缺失”的状态会清记录并 drop 唯一副本。现在要求快照的每一部分都有正面证据：staged 部分在索引或 HEAD 中，未暂存/未跟踪部分必须回到工作区；缺失时只补回没人改过的路径（`git restore --source=<stash>` / `--source=<stash^3>`），有冲突（路径已被改成别的内容）则保留记录并告警。无论结论如何都不再删除 stash。
- **VSIX 里带着完整 TypeScript 源码**：esbuild 的 `sourcemap: true` 让 `dist/extension.js.map` 内嵌 `sourcesContent`，安装包里可读出全部源码。现在 release 构建默认不生成 sourcemap（仅 `--watch` 或显式 `--sourcemap` 时生成），打包前会删除上一次遗留的 `.map`；`release.yml` 增加门禁，VSIX 中出现任何 `.map` 即发布失败。
- **按过期 `stash@{n}` 丢弃可能删错 stash**：Git 没有按 sha 的 `stash drop`，并发 `stash push` 会移动下标。该 drop 实现已随自动删除一起退役；现在只把 `stash@{n}` 当作**显示给用户的提示**，横幅里同时给出 sha 与可复制的 `git stash drop <name>`，由用户在自己看到当前列表后决定是否执行。槽位名在**每一轮恢复检查时重新解析**（不是缓存在首次出现的值上），因此横幅会跟随当前槽位，避免指着已经被其他 stash 占用的下标。注意这是按恢复检查的节奏刷新，不是每次界面重绘都去查询 Git。stash 已不对应任何槽位时，插件只报名称无法解析，绝不声称执行过删除。
- **横幅给出的恢复命令在 reflog 损坏时跑不通**：槽位无法解析时，旧实现把目标拼成 `stash:<短 sha>`，而 Git 没有这种引用（`error: stash:xxxxxxx is not a valid reference`），偏偏这正是该提示存在的场景。现在回退到 **sha 本身**（`git stash apply --index <sha>` 可用）；由于 Git 同样不支持按 sha 执行 `stash drop`，槽位未解析时**不再提供 drop 命令**。回归用例会真正在临时仓库里**执行**横幅打印出的每条命令并断言退出码为 0，而不是只比对字符串。
- **进程回收用例的判活方式无效**：Git for Windows 的 hook 写出的 `$!` 是 MSYS pid，用例却用 Windows 的 `process.kill(pid, 0)` 探测，两者属于不同命名空间——通过时是**空洞的**（无法发现回收回归），偶尔还会误报失败，使发布门禁不稳定。现在 hook 改为写出 `/proc/$!/winpid`，按真实的 Windows pid 判断，并在断言“已被回收”之前先断言它**确实存活**（正向对照，防止 pid 从未有效却让断言空过）。
- **测试自身泄漏循环进程**：`runGit settles on exit…` 的 hook 用 `while [ ! -f marker ]` 无限循环，清理时先写 marker 再删目录；删除一旦先于 shell 看到 marker，循环就会在已删除的临时目录里永远运行。现在循环带上次数上限，且清理时先等孙进程退出再删目录——连续多次运行后进程表干净。
- **恢复流程在锁外执行 Git 写操作**：过去只在入口做一次 `isBusy()` 检查，随后 6–14 次 Git 调用都不持锁，可能与变基/暂存并发写 index。现在整轮对账在 mutation lock 内执行，忙时跳过并在下一次空闲轮询重试。
- **单飞 key 被同步异常永久占用**：`RecoveryCoordinator.run` 过去在异步任务启动后才登记 `inFlight`，`task` 同步抛错会让 key 永久留在 map 中。现在先登记再放行任务，并使用 `finally` 清理。
- **`stop()` 可能在 pid 回收后误杀进程**：子进程已 `exit`、仍处于输出排空的宽限期时，`killProcessTree()` 仍会按旧 pid 发送信号。现在 `exited` 后只安排结算定时器，不再追发 kill。
- **对账阻塞渲染**：对账过去在 `refresh()` 里被 `await`，每次 `stashPresence` 约 3 秒、整轮约 7 秒，而轮询间隔仅 1.5 秒。现在对账移到渲染之后异步执行，并对持续失败做指数退避（最长 30 秒）。
- **测试未纳入类型门禁**：`tsconfig.json` 只包含 `src/**/*.ts`，导致测试目录内的类型错误不被发现。新增 `tsconfig.test.json`（`src` + `test`，`noEmit`）并接入 `npm run typecheck`，同时修复了暴露出的类型错误。

### 🔒 安全与可靠性

- 写操作仍然串行化：mutation gate 的 read / UI / mutation 分类与 paused-rebase allow-list 不变，读操作、滚动、指针、IME 和刷新永不被写锁阻塞。
- 锁释放按 owner 身份校验，迟到的 `finally` 不会清除较新的 owner；`forceRelease` 只在用户明确要求时使用，且之后必然重读 Git 状态。
- 日志复用并扩展了凭据脱敏（URL userinfo、`Authorization`、token/password/api-key 等键值与参数），日志写入失败（只读目录、磁盘满）只会关闭文件日志，不影响任何插件功能；日志不写入仓库目录。
- 新增回归测试（当前全量 **214 项**，`npm run test` 全绿）：写锁的获取/拒绝/owner 校验/自愈/看门狗文案/强制解除后重读 Git 状态/已结算 owner 回收，文件日志的路径、脱敏、轮转、保留与失败容忍，`exit` 结算与超时/取消只结算一次的进程树回收尝试，侧栏 tooltip 与右键菜单的 DOM 行为，以及待恢复改动对账（已应用快照静默清除且 **stash 保留**、stash 已消失的空记录静默清除、只恢复一次、冲突时保留、amend 落地后才结算、未完成追加保持 pending、reset 只清孤儿记录、reset 在无法验证时保留记录、日志记录 stash 名与原因；后续 commit 修改同一路径仍能结算、`reset --hard` 丢弃快照后仍保留、索引匹配但未跟踪内容只在 stash 时补回、残留路径被改成新内容时保留记录且不覆盖）、告警去重与恢复单飞、恢复横幅不遮挡 commit 列表。
- 追加完成判定回归：`amend` 后同一文件被后续 commit 修改仍能结算（并断言最终 blob 与快照不同）、`reset --hard` 丢弃快照内容时必须保留记录、索引匹配但未跟踪文件只在 `stash^3` 时必须补回工作区而不是清除记录、未提交部分的路径已被写成新内容时必须保留记录且不覆盖该内容。判定改为 `git ls-tree` 逐路径比对 **mode + object** 后，退役了三代只为“是否允许 drop”服务的启发式：`git rev-list --objects <rev> --not <since> -- <path>`（只列区间内新引入对象，会剪掉复用 blob：仅模式变化、内容回退、目录整体移动）、`git log --format= --raw -M --full-history` 扫描（revert 形状的 amend 不产生 raw 记录）、`git log --find-object=<blob>`（同字节出现在其他文件即误判）。它们随自动 drop 一起删除，没有留下死代码。残留的已跟踪路径只在与快照内容一致或路径缺失时写回（不再把“工作区等于 HEAD”当作未改动，否则会覆盖用户已提交的更新内容）。`streamChat` 的 deadline 用例从 20 ms 放宽到 1 s 并断言确实是 deadline 结束流——20 ms 在负载较高的机器上可能先于首个 SSE delta 触发，使 `chunks` 为空而与客户端行为无关。
- 失败模式回归（针对评审发现的探测假阳性）：逐一让每项探测失败——`^1`（base）、`^2`（index）、`^3`（untracked commit）、`^3` 的树对象缺失，以及 `git diff --cached` 非零退出——记录都必须保持 `pending`/`unknown` 且 stash 完好；`^3` commit 缺失时 stash 仍声明三个 parent，因此必须按“探测失败”而不是“没有未跟踪内容”处理。reflog 损坏时 `git stash list` 返回空也不得当作 stash 已消失，必须保留记录并告警；`git reset --hard` 后 HEAD 缺文件时不得仅凭祖先关系清除记录。另按新的不变量补了“确认已落地 → 结算且 stash 仍在”“仅模式变化 / revert + 后续编辑 / 目录重命名 / 同字节巧合 → 保留记录、保留 stash、显示横幅”“一次完整恢复过程不出现任何 `stash drop|pop|clear` argv（Git 调用观察器）”“reset 拒绝删除仍保存内容的 stash 并说明原因”等用例。
- Provider 级回归（真实 `vscode` stub + 真实 Git 临时仓库）：`dismissRecoveryNotice` 消息真正写入去重状态，随后 `refresh()` 不重建横幅，且推送给 webview 的 state 也不携带该横幅；另有一个用例在横幅已装填后由并发 `stash push` 把记录对应的 stash 压到 `stash@{1}`，断言横幅改述新槽位、不重复弹窗，且关闭横幅后即使槽位再漂移也不会复活；`resetExtensionState` 在内容无法验证时保留记录并报告“已保留”；恢复轮次与 mutation lock 不重叠（持锁时整轮跳过、释放后下一次结算）；`forceReleaseMutationLock` 重读 Git 而非相信内存；已结算但未释放的 owner 被回收；看门狗对同一 owner 只告警一次、外部 owner 的迟到 `disarm` 不会取消它、触发后自行清理。

### 使用方式

- 下载 `git-rebase-visual-0.8.0.vsix`。
- VS Code：扩展面板 → `...` → **Install from VSIX...**。
- 命令行：`code --install-extension git-rebase-visual-0.8.0.vsix`。

### 功能总览

- 交互式 rebase：拖拽重排、Alt+Arrow 重排、edit/reword/squash/fixup/drop、冲突 Continue/Abort；
- 提交保护：patch-id 锁定、Push guard、`--force-with-lease` 与受控 Undo；
- 工作区辅助：Staged/Changes 文件列表、单文件与批量 stage/restore/unstage、VS Code 左右 Diff、auto-stash 与 stash list；
- AI message：流式生成、deadline、取消、trailer 保留与 staged-only commit；
- 诊断与质量：OutputChannel、带轮转与脱敏的会话日志、可解释的写锁与看门狗恢复、真实 Git 集成测试、webview DOM 回归、VSIX 内容门禁。

### 文件

- **`git-rebase-visual-0.8.0.vsix`** — VS Code 离线安装包。

### 系统要求

- VS Code `^1.85.0`
- Git `2.31.0+`
- 本地安装可运行 extension host 的 Node/Electron 环境（VS Code 自带）。
