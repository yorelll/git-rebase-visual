## Git Rebase Visual 0.8.3

用于 VS Code 的可视化交互式 Git rebase 扩展：在侧边栏中安全地重排、编辑、锁定和推送 commit，并提供工作区恢复、只读 Diff、AI commit message、stash 与受控 Undo。

> 来源：Git tag `v0.8.3` · GitHub Actions 自动构建 · CI 将执行 `npm run test:release`、VSIX 内容校验与版本记录校验。

### 🐛 修复（0.8.3）

- **点击未跟踪文件的 `⌫` 报“缺少要恢复的文件状态”，文件也没被删除**：左侧“未提交的改动”里，**Changes 分组中每一次单文件恢复**都被宿主拒绝——不只是 `⌫`（删除未跟踪文件），`↶`（恢复此文件的工作区改动）同样中招。
  - **原因**：webview 直接把分组的键当作恢复侧别发送。分组的键是 `staged` / `unstaged`（表示这一行属于哪个分组），而宿主的侧别词表是 `staged` / `working`（表示要恢复索引那一半还是工作区那一半）。宿主只接受后者，于是 `side: "unstaged"` 一律被判定为非法并抛出“缺少要恢复的文件状态”。
  - **修复**：在消息边界翻译一次，其余不变。宿主的词表保持 `working` / `staged` 单一口径，**没有**加入 `unstaged` 作为第二个别名——两套词汇并存只会让下一个改动再次踩到同一个坑。三个入口全部覆盖：`⌫`、Changes 的 `↶`、Staged Changes 的 `↶`（后者本来就正确，一并固定）。
  - **验证不是靠断言字符串**：一条用例把 webview **自己发出的**消息原样送进真实宿主处理器，断言文件真的被删除、工作区改动真的被丢弃、暂存真的被撤销且内容仍留在工作区。只把断言里的字符串改成 `working` 而没修好宿主契约时，这条用例依然是红的。
- **折叠的锁定 run 摘要少了一个空格**：曾显示 `🔒 :3 lock · no push · la ×1`，现为 `🔒 : 3 lock · no push · la ×1`。同一行里的作者列表（` · la ×1 · sa ×1`）与待重放后缀（` · replay`）拼接不变；屏幕阅读器读的是单独生成的 `aria-label`（`已锁定 N 个 commit，不会被推送；…`），本来就不读这行紧凑文本，因此不受影响。
- **Push 提示只显示 refspec，看不出推了什么、推到哪里**：进度标题与成功提示原先形如 `推送中：HEAD:refs/heads/master → origin`。现在进度标题、成功提示与失败提示都写明同一组三件事——**推送方式**、**这次推送的 commit 标题（不是 hash）**、**目标分支**：

  ```text
  推送中：普通推送："feat(cmos_sensor): add ir ispll" → origin/fpga/rle1283_rts3923
  已推送：普通推送："feat(cmos_sensor): add ir ispll" → origin/fpga/rle1283_rts3923
  ```

  - **推送方式**取用户在选择框里点的那一项（**普通推送 / 评审推送 / 自定义推送**），由做决定的那一步随 refspec 一起带到提示里，**不从 refspec 字符串反推**——自定义的 refspec 完全可能与普通推送一模一样，反推会给出错误的标签。
  - **commit 标题**而不是 hash：hash 对用户不可识别，且会让人怀疑推送的是不是另一条 commit。标题超过 60 个字符时截断并加 `…`；截断按**字符（码点）**进行，不会把一个 emoji 之类的代理对切成半个。
  - **目标分支取自实际使用的 refspec 的目的端**，而不是 upstream 分支。这两者在正好是本项目支持的几种推送里会分叉：评审推送写 `refs/for/<branch>`（不碰 upstream 分支），自定义 refspec 可以写任何 ref。`refs/heads/<分支>` 显示为 `origin/<分支>`；其他 ref 显示为 `origin:<ref>`（例如 `origin:refs/for/master`），不会被误认为某个被推送的分支。无法可靠判定时如实显示 **（无法确定目标分支）**——一个看起来合理的错误分支比一句含糊更糟。
  - **失败路径同样携带三要素**：`推送失败：普通推送："…" → origin/master。<Git 的原始错误>`，并在原有逻辑里照旧写文件日志。用户不需要先记住自己点了哪种推送、推的是哪条 commit，再去读错误。
  - **失败与成功互斥**：失败路径此前用 `return` 跳出进度回调，而成功提示在回调之外，导致一次失败的推送会同时弹出红色的“推送失败”和绿色的“已推送”。现在失败路径抛出专用控制流异常，由调用方吞掉并补一次 `refresh()`，**任何一次推送只会报告一个结果**。取消仍然走原来的取消异常。
  - **远端名本身带斜杠时目标分支会算错**：`getUpstream` 曾把 `@{upstream}` 按第一个 `/` 切成远端与分支，远端名是 `team/origin` 时会得到 `team` + `origin/master`——评审推送实际打到了另一个远端，而提示仍写着 `team/origin`。现在改为让 Git 自己解析（`git for-each-ref` 的 `%(upstream:remotename)` / `%(upstream:remoteref)`），并在远端名不在 `git remote` 名单内时直接显示 **（无法确定目标分支）**。远端跟踪 ref 已被 `fetch --prune` 清掉时不再返回一个用了就报 `unknown revision` 的名字：`getUpstream` 用同一次 `for-each-ref` 里的 `%(upstream:track)` 判定——`[gone]` 即视为没有可用上游，按「未配置 upstream」给出一条可见的中文提示——这条路径此前会让一次推送完全没有反馈。（同一轮的前一个版本曾用第二次 `git rev-parse --verify refs/remotes/<remote>/<branch>` 做存在性检查，那个拼出来的路径对重命名/嵌套的 fetch 命名空间会误报，且每次多花约 330 ms；现已被读取 Git 自己报告的原子取代。）回归用例在同一仓库放了一个名为 `team` 的诱饵远端，断言提示为 `team/origin/master` 且诱饵远端上没有任何 ref 被创建。
  - **commit 标题不再恒取 `HEAD`**：标题改由 refspec 的**源端**解析（去掉 `+` 前缀、取冒号左侧，无冒号时用整个 refspec），因此 `git push origin HEAD~1:refs/heads/x` 报的是真正推送的那条 commit，而不是当前 HEAD。解析不出源端时才回退 `HEAD`。
  - **没有变化时不再说“已推送”**：删除一个不存在的远端分支（`:refs/heads/<missing>`）时 Git 退出码为 0，此前会报告“已推送”却什么都没变。现在识别 `Everything up-to-date` 与 `deleting a non-existent ref`，改报 **`无需推送：…（远端已是该状态）`**。判定读取的是 Git 的英文输出，因此推送子进程固定 `LC_ALL=C`。
  - **本地跟踪上游与删除型 refspec 的措辞**：`branch.<b>.remote = "."`（`git branch --set-upstream-to=other` 的常见产物）不是远端，Git 对它的 `%(upstream:remotename)` 返回字面量 `"."`。此前确认框会写 `推送到 ./other？`、通知却写 `（无法确定目标分支）`，同一次推送两处互相矛盾。现在 `getUpstream` 把 `"."` 视为无远端，`pushDestination` 也独立拦截它，确认框与通知共用同一份 `git remote` 名单。另外 `:refs/heads/<branch>` 这种只删除远端 ref、不发布任何 commit 的 refspec 不再把 HEAD 的标题写成这次推送的内容，改为 `自定义推送：删除远端 ref → origin/<branch>`。
  - **取消推送不再成为未处理异常**：`gitRebaseVisual.push` 的命令注册是 fire-and-forget，用户取消时 `pushBranch` 抛出的异常会直接进扩展宿主日志。现在注册处带 `.catch(...)`，经诊断日志记录一条，不弹窗（主动取消不是错误）。
- **“仅生成 message（不提交）”入口的位置**：这是**唯一**不写 Git 的 compose 入口（其他入口最终都会提交；弹窗里的 **复制 message** 也只在 `messageOnly` 模式下显示）。
  - edit 停靠时，它在**横幅的编辑操作区**与**「更多提交选项」**里各出现一次，两处发出同一条消息（HEAD 起即如此，本次未改动，测试按区域分别断言）。
  - 冲突暂停与普通暂停时各出现一次——此时横幅只有 Continue/Skip/Abort，而宿主的暂停策略会拒绝其他 compose 目标，所以它是那里唯一的草稿路径。
  - 未暂存任何内容时也会出现：这是唯一能以 `working` 模式针对工作区起草的入口。
  - **唯一省略**：空闲且改动全部已暂存。用户认为这一状态下它与 Staged Changes 的 `✦` 重复，因此按要求省略；需要说明的是即便在这里它也仍是唯一不写 Git 的路径，省略它是在满足用户的取舍，而不是因为它已被完全覆盖。曾经把它从所有非停靠状态一并删除的尝试，同时删掉了唯一的 `working` 模式入口和暂停期间的唯一草稿路径，已纠正。
  - `messageOnly` 机制本身**没有删除**：暂停 rebase 的白名单判定、Compose 面板的 `messageOnly` 分支（标题文案、**复制 message** 按钮、`apply` 走复制而不是提交）都继续依赖它。

### 🔒 安全与可靠性

- 本轮改动**不触碰**任何 Git 写入路径：恢复侧别的翻译只改变了消息字段，恢复本身的命令与前置校验（重新读取 porcelain、未跟踪文件删除前的二次复核、暂存/工作区两侧的分别恢复）保持不变。
- Push 通知的改动只影响提示文案、进度标题与 upstream 的解析方式；锁定检查、`--force-with-lease`、评审推送与自定义 refspec 的行为完全不变。推送方式与目标分支都由决定推送的那一步带出，二者不会出现“提示说普通推送、实际推的是评审 refspec”的分叉。`getUpstream` 现在读取的是 Git 自己解析的远端名与远端分支，不再自行切分 `@{upstream}`，因此带斜杠的远端名不会再把推送引到另一个远端。
- 新增的推送用例使用真实 bare 远端验证成功路径，失败路径使用“已配置但不存在”的远端以得到跨平台稳定的错误；两种情况都断言提示里**不出现 40 位 hash**。评审与自定义两种推送各自有真实远端用例，断言提示里的目标与该远端上真正移动的 ref 一致；自定义分支另有 `showQuickPick` / `showInputBox` 的调用记录作证，避免模板为空时悄悄退回默认路径却让用例空转。
- 带斜杠远端名的用例把 `remote.team/origin.url` 与 `remote.team.url` 直接写进 `.git/config`，并断言诱饵远端上没有被创建任何 ref——若实现退回“按第一个 `/` 切分”，该用例会以 `actual: 'team'` / `expected: 'team/origin'` 失败（已实测），而不是仅仅换了一种说法通过。
- 完整套件 **324 项**通过、0 失败、0 跳过，从确认干净的进程表运行。

### 使用方式

- 下载 `git-rebase-visual-0.8.3.vsix`。
- VS Code：扩展面板 → `...` → **Install from VSIX...**。
- 命令行：`code --install-extension git-rebase-visual-0.8.3.vsix`。

### 功能总览

- 交互式 rebase：拖拽重排、Alt+Arrow 重排、edit/reword/squash/fixup/drop、冲突 Continue/Abort；
- 提交保护：patch-id 锁定、Push guard、`--force-with-lease` 与受控 Undo；
- 工作区辅助：Staged/Changes 文件列表、单文件与批量 stage/restore/unstage、VS Code 左右 Diff、auto-stash 与 stash list；
- AI message：流式生成、deadline、取消、trailer 保留；
- 诊断与质量：OutputChannel、带轮转与脱敏的会话日志、可解释的写锁与看门狗恢复、真实 Git 集成测试、webview DOM 回归、VSIX 内容门禁。
