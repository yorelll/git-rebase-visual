## Git Rebase Visual 0.8.2

用于 VS Code 的可视化交互式 Git rebase 扩展：在侧边栏中安全地重排、编辑、锁定和推送 commit，并提供工作区恢复、只读 Diff、AI commit message、stash 与受控 Undo。

> 来源：Git tag `v0.8.2` · GitHub Actions 自动构建 · CI 将执行 `npm run test:release`、VSIX 内容校验与版本记录校验。

### 🐛 修复（0.8.2）

- **“追加到 commit”把后续 commit 的文件误报为冲突（`Index was not unstashed.`）**：只暂存**一个**文件、把它追加到某个 commit 时，插件可能报 `恢复暂存区失败：Index was not unstashed.`，并把若干**后续 commit 才引入**的文件列为冲突。
  - **影响范围比最初报告更广**：不只“最早的那个 commit”。只要追加目标**早于 tip**，就可能失败；目标恰好是 tip 时不会触发这个 `apply --index` 合并冲突。用户报告中的“最早 commit”只是其中一例。
    - 但“目标是 tip”并不等于安全：路径名含非 ASCII、以空格开头或含 `*`/`?`/`[` 时，即使目标是 tip，旧解析也会把这些路径静默丢掉却仍报告成功（见下方“路径名会让恢复到‘静默空转’却报告成功”），因此不存在“目标恰好是 tip 就总能成功”的情形。
  - **冲突本身是伪造的**：每个 commit 只添加自己的文件，目标 commit 的树与后续 commit 的路径毫无关系，因此 `CONFLICT (modify/delete)` 不可能成立。
  - **没有丢失任何用户数据**：`git stash apply --index` 失败时 stash 仍完整保留；选择 Abort 后工作区干净、stash 仍在，`reconcilePendingStash` 能把三份改动按原暂存/未暂存状态完整放回。任何一步失败都只写内容、不动条目；成功结算后插件只删除自己创建的那一条（见本节末尾“只删除自己创建的 stash 条目”）。
  - **原因**：`stashPush` 保存的是**整个工作区**，而 `stashApplyIndexBySha` 用 `git stash apply --index` 恢复。该命令会合并 stash 的**工作区那一半**，于是在只包含目标 commit 树的停靠点上，后续 commit 才有的路径变成 “Updated upstream 中已删除 / Stashed changes 中已修改” 的假冲突，整次恢复以 `Index was not unstashed.` 中止。真正需要恢复的暂存部分（`stash^1..stash^2`）其实只有那一个文件。
  - **修复方式**：不再用 `apply --index` 合并，而是把快照的**三个部分各自从自己的树**恢复，只触碰快照自己的路径：
    1. 工作区部分 —— `stash^1..stash` 的路径，`git restore --source=<stash> --worktree`
    2. 暂存区部分 —— `stash^1..stash^2` 的路径，`git restore --source=<stash>^2 --staged`
    3. 未跟踪文件 —— `stash^3` 树，`git checkout` 后 `git reset` 保持其为未跟踪
  - **两条必须遵守的顺序/参数**（均已写入代码注释）：工作区部分必须**先于**暂存区部分——先应用“暂存删除”会让该路径离开索引，随后 `restore --worktree` 无法解析 pathspec（`pathspec did not match any file(s) known to git`）；枚举路径的 `git diff` 必须带 `--no-renames`，否则重命名会被折叠成只剩目标路径、旧路径残留在索引里。
  - **失败即保守**：任何一步非零都保持 stash 不动，并在 `message` 中写明是哪一步失败（`恢复工作区失败` / `恢复暂存区失败` / `恢复未跟踪文件 ... 失败`）。
  - **曾被评估但不可用的方案**：`git read-tree <stash>^2` 会**替换整个索引**（不是增量合并），实测使得随后的 `commit --amend --no-edit` 把五个文件全部提交进目标 commit；`git stash push --staged` 与 `--include-untracked` **互斥**会被直接拒绝，单独使用又会留下脏工作区使 rebase 无法开始，且它需要 Git 2.35+ 而本扩展的下限是 2.31.0。两者都已放弃。
- **失败后的提示把用户引进死胡同**：追加在 amend 之前失败时，提示曾写“请解决冲突后 Continue 或 Abort”。但 Continue 命令本身在该状态（`amended: false`）会拒绝执行，因此“Continue”是条走不通的路。提示已改为明确说明**暂存内容尚未写入目标 commit、无法 Continue，请 Abort 自动恢复**，并保留原因说明。
- **静默放弃追加（第二个独立缺陷）**：若用户照旧提示把“冲突”文件 `git add` 后，索引恰好与快照一致，对账会判为 `resolved` 并清除记录——而此时变基仍停靠在原目标上、追加从未 amend，用户的暂存意图就这样被无声丢弃。
  - 现在 `reconcilePendingAppend` 只在**追加确实落地**时才判定完成（`stagedSnapshotInHead` 确认内容已进入 HEAD，或记录本身标记 `amended`）。若目标仍是祖先且变基仍在进行中，即使索引已与快照一致也**保留记录**，并明确提示“追加未完成”。
  - 用户显式 Abort 之后不再有进行中的变基，同一状态即视为真正的成功（用户主动放弃了这次追加），记录会正常结算，不会永久告警。

- **路径名会让恢复到“静默空转”却报告成功**：`git diff --name-only` / `ls-tree` 的输出在 `core.quotePath` 为默认值（`true`）时会把非 ASCII 路径写成带引号的八进制转义串（`"\346\226\260..."`），该字符串不是路径，`cat-file -e HEAD:<它>` 必然失败。于是两处“是否已存在”的判断都判为不存在，路径被直接丢弃，函数仍返回 `ok: true`，`commit --amend` 与 `rebase --continue` 都成功——界面报告“追加成功”，而文件从未进入 commit。本机 `core.quotePath=false` 掩盖了该问题。
  - 同一类问题还有两种表现：以空格开头的路径被 `trim()` 吃掉；名字含 `*`/`?`/`[` 的路径被当成 pathspec 通配符，可能匹配到错误文件或直接失败。
  - **修复**：所有枚举路径的 Git 调用统一改为 **NUL 分隔**（`-z`）+ 按 `\0` 切分，**不再 `trim()`**；所有把路径回传给 Git 的调用（`restore`/`checkout`/`reset`/`add`/`hash-object`/`diff --quiet` 等）统一带 `GIT_LITERAL_PATHSPECS=1`。覆盖 `worktree.ts` 的工作区/暂存区/未跟踪三部分、`pendingRecovery.ts` 的快照探测与补回、`commitLog.ts` 的冲突文件列表、`worktreeChanges.ts` 的单文件暂存/恢复。
- **恢复路径可能覆盖用户更新的内容**：补回未提交部分时 `git restore --worktree` 未带 `GIT_LITERAL_PATHSPECS`，名字含通配符的路径会被当成模式，例如 `e[1].txt` 会匹配到 `e1.txt`，把用户新写的内容覆盖成快照旧内容。已修正为按字面匹配。
- **提示会先给出一个必定失败的命令**：当记录保持 `pending`、且快照的暂存区部分**非空且已在索引中**时，`git stash apply --index` 必然返回 `already exists in index … Try without --index`。现在命令列表按探测到的实际状态生成（这种情况下不再给 `--index`，并明确以 Abort 为主操作），并有测试**真正执行**提示中的第一条命令并断言退出码为 0。
  - 这里必须区分“暂存区已就位”的两种来源：快照**本来就没有**暂存区部分时 `index` 同样是 `present`，但此时 `apply --index` 没有可合并的内容、会正常成功，因此判据用暂存路径数（`indexPaths > 0`）而不是仅看 `index`。这一区分由既有用例（`reset refuses to drop a content-bearing stash and says why` 要求提示里仍出现 `apply --index`）钉住。
- **提示的 Abort 也可能失败**：原先先写工作区部分再 amend；若 amend 被拒（例如 `pre-commit` 钩子），属于后续 commit 的路径会以未跟踪文件留在工作区，`git rebase --abort` 随即以 `untracked working tree files would be overwritten by reset`（128）失败，形成永远重试不完的死胡同。
  - 追加事务现在**先只恢复索引/未跟踪部分 → amend → 成功后再恢复工作区部分**，失败的 amend 不会留下任何未跟踪残留。
- **Abort 永不删除任何文件（本轮最重要的变更）**：`git rebase --abort` 会被“未跟踪文件会被回退覆盖”挡住（`untracked working tree files would be overwritten`，128）。此前的实现会在“证明删除无损”时自动删掉阻挡路径，把 abort 做完。**这条路走不通，已彻底移除**。
  - **为什么放弃自动删除**：三轮审查各发现一种“证明为无损、实际会丢字节”的形状——先是归属证明（只证明“曾在本 HEAD 里”，不证明盘上字节属于本次变基），接着是预测源的属性基准（`cat-file --filters` 读工作区，`reset --hard` 读目标树），最后是相对路径的 `core.attributesFile` 与被 smudge filter 读取的工作区状态。每一次修补都只封住一种形状，下一种立刻出现。原因是这个类**无法穷举**：它的定义是“检出过滤器可能依赖 blob 之外的一切”，而 Git 的过滤器可以执行任意命令、读任意文件。任何一次预测错误都会删掉可能不存在于任何 commit、也不存在于任何 stash 中的字节。
  - **现在的行为**：abort 只调用一次 `git rebase --abort`。成功就返回；失败时**只认 Git 自己给出的碰撞文案**，用它来**列出路径**，然后抛出错误。**没有任何分支会删除文件**（目录碰撞同理）。
  - **错误信息按这个顺序写**，目的是让从没读过这段代码的用户一次就能处理完：① 发生了什么——abort 被哪些未跟踪文件/目录挡住，逐条列出 Git 给出的原始路径；② **明确说明“没有删除任何文件”**——abort 失败时用户最怕的就是这个；③ 下一步怎么做——把这些路径移出仓库或改名后重新 Abort，并给出可直接复制的 `mv <path> <path>.bak` 命令（超过 5 条时只列前 5 条并注明还有几条），同时提示 Windows 用户可在资源管理器里重命名；④ 你的改动没丢——**按 `git stash list` 的实测结果**说明（见下一条），变基仍停在暂停状态，停在这里没有任何损失；⑤ 如果某个文件其实是构建产物、不需要保留，用户可以自己删掉它再重试——但这个判断由用户做，扩展不替他决定。
  - **可复制的 `mv` 命令对 shell 正确转义**：路径用 POSIX 单引号包裹，内部的 `'` 按 `'…'\''…'` 闭合重开。此前只是把路径塞进 `'…'` 里，于是合法文件名 `it's.txt` 生成 `mv -- 'it's.txt' 'it's.txt.bak'`——粘到 shell 里直接失败；更糟的是 `pwn'; touch OWNED; echo '.txt` 这种名字会**执行别的东西**。扩展自己从不执行这些字符串，但它们的唯一用途就是被复制，所以错的命令就是真实缺陷。正确性不是靠肉眼看引号，而是靠一条单测把每个恶意文件名丢进真实 `sh -c 'printf %s <quoted>'` 再逐字节比对回来的字符串（`'`、`"`、反引号、`$`、空格、换行、前导 `-`、非 ASCII、`\`，以及上面那个执行载荷），并断言探针目录里**没有**出现 `OWNED`。把 `shellQuote` 换回旧的未转义写法后该用例立刻变红。
  - **“改动还在 stash 里”改成条件式**：此前消息无条件断言“原始改动仍完整保存在 stash 中”。当 `gitRebaseVisual.autoStash` 关闭、或变基由用户手动发起时，`git stash list` 为空——用户第一个想到的命令就能当场推翻这句安慰，而一句能被立刻证伪的安全声明会连带削弱整段消息的可信度。现在 `describeStash` 先跑 `git stash list --format=%gd` 再措辞：有条目就报**实测条数**（不描述条目内容，那它没有检查），为空就明说“`git stash list` 现在为空，没有 stash 副本可以依赖；但你的工作区原封未动”。两种分支都成立的那半句（没有删除任何东西、变基仍暂停）始终保留。
  - **目录碰撞**用同一套保证和同一种语气：单独识别 `Updating the following directories would lose untracked files in them` 这条文案，点名目录，说明“没有删除任何文件，也没有删除任何目录”，并给出适合目录的处理建议。
  - **不认识的失败形状**仍然原样抛出 Git 输出。由于整个函数没有任何删除分支，未识别的形状不可能导向删除——这条现在是**结构性的**，不再依赖“解析没匹配上”的巧合。
  - **代价（据实说明）**：遇到历史遗留的碰撞状态时，用户需要多手动做一步（把文件移开），而不是点一下 Abort 就自动完成。这是有意的取舍：多一步手动操作，换掉一整类无法枚举的静默丢字节风险。上文的追加事务已改为“先索引/未跟踪 → amend → 再工作区”，本身不再产生这类残留，所以需要这一步的情况应当很少。

### 🧪 测试

- 新增集成回归，全部用真实 Git 复现：
  - 用户报告的原始形状（暂存一个文件追加到最早 commit，后续 commit 的路径不得进入索引）；
  - 暂存**新文件** + 后续 commit 文件上有工作区改动（修复前同样失败）；
  - 纯**修改**后续 commit 的文件、**既无未跟踪文件也无工作区残留**（最能说明问题的最简形状，修复前失败）；
  - 暂存**删除**（修复前就通过，用于固定行为、防止朴素修复把它改坏）；
  - “索引与快照一致但追加未落地”必须保持 `pending`，且 Abort 后能正常结算；
  - **路径解析**：把 `core.quotePath` 显式设为 `true` 后，同一次追加里同时包含中文名、前导空格名和 `br[1].txt`，断言三者都真正进入 amend 后的 commit，且诱饵 `br1.txt` 的 blob 未被改动；
  - **Abort 死胡同**：用会拒绝的 `pre-commit` 钩子让 amend 失败，断言 `git rebase --abort`（及其后的 `abortRebase`）能完成、历史回到变基前、stash 仍可恢复出原始工作区改动；
  - **Abort 不再自动删除**：旧的“恢复边界”“碰撞路径被用户改写”“clean/checkout 三种形状”用例全部改写为契约测试——它们现在断言的是**拒绝 + 字节不变**，而不是“在可证明无损时删除”。具体见下方契约测试列表。
  - 用会拒绝的 `pre-commit` 钩子让 amend 失败后，`abortRebase` 在干净工作区上仍能完成（历史回到变基前、stash 仍可恢复出原始工作区改动）——这是“无阻挡时必须成功”那条回归用例的现实来源。
  - **目录碰撞**：把阻挡路径换成同名目录并放入 `keep.txt` → `abortRebase` 抛错、错误信息点名该目录并说明未删除任何文件/目录，目录仍是目录、`keep.txt` 字节不变，变基仍停在暂停态。
  - **不认识的失败形状**：把 `.git/rebase-merge/orig-head` 改写成全零（Git 报 `invalid orig-head`，不匹配任何碰撞文案）→ `abortRebase` 抛错，两条用户文件（`later.txt`、`mine.txt`）字节全不变；
    这条用例现在守的是一个结构性事实：`abortRebase` 里根本不存在删除分支，所以未识别的形状不可能导向删除，而不只是“某段文案没匹配上”。
  - **字面 pathspec**：`worktree.ts` 与 `worktreeChanges.ts` 的**全部 9 个**站点，每个都由一个“诱饵在该次调用发生时持有目标永远没有的内容”的夹具钉住（逐个站点单独撤掉 `GIT_LITERAL_PATHSPECS` 都实测变红）。逐点对照见下方 **附录 A**；
  - **告诉用户的命令必须能跑通**：取横幅（`recoveryCommands`）的第一条命令，在真实状态上执行并断言退出码为 0；
  - **顺序回归**：暂存删除形状下断言路径在索引与工作区都被真正删除——把“工作区先于暂存区”调换后该断言变红；
  - **`apply --index` 失败但内容探测看起来完整**：快照的暂存半已在索引、工作区半与一次删除冲突，`git stash apply --index` 退出码 1 而 `stashPresence` 之后的 `complete` 为 `true`——必须保持 `pending` 并保留 stash，而不是报 `restored`。
- 已实测非空转：逐个撤掉对应修复后，相应用例确实变红，恢复后全绿。
  - 追加改写、Abort 死胡同、路径解析（`-z` / `trim()`）、横幅命令、恢复顺序各自的用例。
  - **字面 pathspec**：`appendStaged` 的诱饵改为“目标提交之后才被改写”，去掉 `worktree.ts` 的 `GIT_LITERAL_PATHSPECS` 后该用例变红；`worktreeChanges` 的单文件暂存用例的诱饵在工作区带一处未提交改动（暂存一个干净的诱饵与不碰它无法区分），去掉环境变量后 `stageWorktreeChange` 会把诱饵一起暂存，用例变红。其余 6 个站点本轮补齐了夹具，见附录 A 的“单独撤掉后”一列。
  - **Abort 永不删除文件**（本轮的契约测试，全部用真实 Git）：
    - `abort refuses an untracked collision, deletes nothing and keeps the rebase paused`：碰撞路径的字节与执行前**逐字节相同**、错误信息里出现该路径与“没有删除任何文件”、stash 列表不变、变基仍停在暂停态、HEAD 没有移动；同一个仓库里另一个无关用户文件也原样保留。
    - `a second abort succeeds after the user moves the collision file aside`：把文档里的恢复步骤真的走一遍——先拒绝，再把文件改名，第二次 Abort 成功、历史回到变基前、被移动的文件内容与移动前一模一样。这条用例的作用是保证错误信息描述的步骤**确实可用**。
    - `abort succeeds normally when the tree is clean`：无阻挡时 Abort 必须正常完成。没有这条，一个“永远拒绝”的实现会通过上面所有用例。
    - `abort refuses a CRLF file whose normalization equals the committed blob (eol=lf)`：N-2 的形状保留为廉价回归——先断言 `hash-object --path=` 确实等于 blob（所以“哈希一致就删”的规则会在此删除），再断言拒绝且字节不变。
    - `abort refuses when a relative core.attributesFile changes the checkout form`（N5-1）：相对路径的 `core.attributesFile` 在仓库根目录生效（`eol: crlf`），但把 `GIT_WORK_TREE` 指向别处后同一查询变成 `eol: unspecified`——这条前提断言直接复现了旧预测器为何必然出错，然后断言 abort 拒绝且字节不变。
    - `abort refuses when a smudge filter reads worktree state`（N5-2）：smudge filter 输出工作区里另一个文件的内容，因此同一个 blob 的检出结果取决于磁盘现状；断言拒绝且字节不变。**前提本身也被断言**：`cat-file --filters` 得到 `STAMP` 而 `cat-file blob` 得到 `later`，两者必须不同。这一步不是装饰——把 filter 换成恒等 `cat` 之后，其余断言全都仍然通过（拒绝照旧发生），只有这条前提会变红，没有它这条用例就守不住它声称的那个形状。
    - `abort refuses a directory collision and keeps the directory's contents`：目录而非文件阻挡时，错误点名该目录、说明没有删除任何文件/目录，目录仍是目录、`keep.txt` 字节不变、变基仍暂停。
    - `an unrecognized abort failure deletes nothing`：把 `orig-head` 改写成全零制造不认识的失败形状，两条用户文件字节全不变。
    - `the abort refusal describes the stash as it actually is, not as assumed`：在同一个仓库里**两种状态都走一遍**——stash 为空时消息必须说“为空”且不得出现旧的“仍完整保存在 stash 中”；压入一条后消息必须报实测的 `1 条记录`，且不描述条目内容（它没有检查过）。
  - **`apply --index` 退出码**：只在 `presence.complete` 判定成功时，“暂存半在索引里、工作区半与某个删除冲突”的用例变红（`restored` 而不是 `pending`）。
  - 暂存删除用例在修复前后都通过（用于固定行为）。

### 🔒 安全与可靠性

- 写操作仍然串行化，恢复流程仍然整轮持有 mutation lock；对账仍然“失败即保守”，任何探测失败都保留记录与 stash。
- **插件只删除自己创建的 stash 条目，从不碰你自己压入的条目**：所有恢复路径（含本次新增的三段式恢复）都只写内容；只有内容被**完整确认**（仍在列表、索引复现暂存那一半、worktree 复现改动、未跟踪文件逐字节一致，四处都是正面探测）之后，插件才把自己那条临时条目删掉。结算后 `git stash list` 与你让插件动手之前**按 sha 集合完全一致**，不会有条目挡在你自己的 stash 前面。
- **恢复成功后不再“静默留条”，也不再要求你自己清理**（修复用户报告的 `git stash pop` 失败）：报告里的失败是插件自己的 `-u` 条目挡在最前面，裸 `git stash pop` 先命中它并以 `could not restore untracked files from stash` 失败。把条目留给用户清理只是把问题挪给用户；自动化语义本来就是 stash → rebase → pop，而 `pop` 会删条目。现在的做法是：用 `apply` 恢复内容（失败可重试、不吞副本），确认内容回来后删除自己的条目。结算时只弹一行“已恢复，插件自己的临时 stash 已删除”。
- **删除为什么要按槽位检查两次**：`git stash pop <sha>` / `git stash drop <sha>` 均非法（实测 `error: '<sha>' is not a stash reference`），只能用 `stash@{n}`；而槽位是**位置**，解析后若有并发 `git stash push`，该槽位会换成用户的条目。因此删除前重读占用者、必须仍等于自己的 sha 才动手；删除后再核对 Git 实际删掉的是哪一条，不符就用 `git stash store` 原样恢复该条目（实测可完整恢复该 commit 与 reflog 条目）。任一步不符都是拒绝并报告，绝不重试。
- **“删除的是哪一条”不能靠英文文案判断**：`Dropped stash@{n} (<sha>)` 是 gettext msgid，在非英语 `LC_ALL` 下会被翻译，正则失配；旧实现此时直接返回“自己那条已删除”，而真正被删的用户条目**再也没被恢复**——整个回滚在最需要它的场景里静默失效。现在判据是**身份**：删除后重新读 `git stash list`，自己的 sha 已不在列表即正确；仍在列表则说明删掉的是别的条目，从“删除前一刻的快照”里找出消失的那一个再用 `stash store` 复原。文案只在无法比对时作旁证，旁证也拿不到就**拒绝并说明无法确认**，绝不谎报成功。
- **“这次 push 是否创建了条目”同理**：旧实现用 `/No local changes to save/` 判断“没东西可存”，再用 `git rev-parse stash@{0}` 取 sha。本地化环境下第一条永不失配，于是干净工作区上的一次 append 会把**用户已有的 stash@{0}** 记成插件创建的条目——一旦其内容后来满足 `complete`，删除的就是用户自己的条目。现在只比 push 前后的 sha 集合：恰好新增一个才是自己的，0 个（没东西可存）或有多个（并发 push）一律不认领。`LC_ALL=C` 仍然传，但只作辅助，判断本身不读文案。
- **同一个 sha 出现在多个槽位时拒绝删除**：用户对仍在列表里的条目执行 `git stash store -m … <sha>` 会产生两个指向同一 commit 的槽位，而删除只能按槽位寻址——总有一个是用户建的。此时按 sha 计数，多于一个就**拒绝并报告**，两个条目都保留；`stashNameForSha` 也不再返回这类歧义 sha 的槽位名，横幅自动退回“只按 sha apply、不提供 drop”。
- **`git stash store` 复原会改变条目位置与 reflog 说明**：复原后的条目位于列表**最上方**，**reflog 说明**（`%gs`，也就是 `git stash list` 打印的那一行）被改写为 `git-rebase-visual restored <sha7>`；而该 stash commit 的**标题**（`%s`，`git log` 里看到的那一行）**不变**，内容与 commit 也完全相同。回滚消息现在把这两个字段都点名写出来——只说“说明文字”是不够的：按 `git stash list` 核对的人会找不到原说明，按 `git log` 核对的人会看到原标题，两种读者需要的是不同的答案。
- **“自己那条已不在列表”不足以证明只删掉了自己的一条**：删除前列表 `[自己的, 用户的]`，删除窗口内用户自己删掉了插件那条、插件的 drop 又删掉了用户那条，删除后列表为空——旧实现看到“自己的 sha 不在列表”就返回 `ok/gone`，用户的条目从此只剩一个待 gc 的悬挂对象，正是本模块承诺绝不发生的事。现在两个方向都看：自己那条不在列表时，仍在删除前的快照里找出**同时消失的其他 sha**；一个都没有才是 `ours-only`，恰好一个就按普通误删用 `stash store` 复原，多于一个则拒绝并点名（无法确定受害者，不猜）。删除前快照读不出来时仍返回 `ok/gone`（没有更好的答案），但消息明确写出**未做前后交叉核对**，而不是假装核对过。这条判据抽成了纯函数 `dropVerdict`，四种形状直接单测，不需要并发也能覆盖。
- **删除前的预检也曾把“读不出列表”当成“栈为空”**：`worktree.stashRemoveBySha` 开头自己跑了一次 `git stash list`，只判断退出码。reflog 损坏时它退出 0 且没有输出，于是函数直接返回“条目已不存在”（`gone: true`）。当时这条路走不通，只是因为调用方 `removeOwnStash` 先检查了 `presence.listed !== true` 并提前返回——这种“靠调用顺序才安全”的写法正是重构后会咬人的形状。现在预检也走同一个 `readStashList`：`unreadable` 一律**拒绝**（`refused: true`）且不做任何写入，只有 `empty` 才算条目已消失。顺带把 `git stash drop` 非零退出的返回值从 `refused: false` 改成 `refused: true`——拒绝就是拒绝，不该在结果里说没拒绝。**审计结果**：`src/` 里 `git stash list` 共 7 处调用，决策点只有一个（`readStashList`）；其余分别是 `stashNameForSha`（读名字+sha，失败返回 `undefined`，而调用方对 `undefined` 的处理正好是“不提供按槽位的 drop”）、`worktree.stashList`（只用于显示）、`rebaseEngine.describeStash`（按条数为提示措辞）、`stashPopManual`（用户显式点击 Pop，空栈是正常情况），以及 provider 里两处只读展示。
- **恢复结果不能靠中文文案判断**：`announceSettled` 原来用 `removal.message.includes("git stash store")` 来区分“删到了别的条目并已恢复”和“自己的条目还没删”。两个方向都实测是错的：`ambiguous` 拒绝的消息以 `…未尝试恢复，可用 git stash store <sha> 逐个恢复` 结尾，于是**什么都没恢复**的拒绝被公告成“删到了别的条目…已原样恢复”；反过来，drop 之后列表读不出来的消息不含这个子串，就被归进“自己的条目还没删”的分支，并给出 `git stash drop stash@{0}`——而那个槽位的占用者此刻**未知**，用户可能删掉别人的条目。现在 `StashRemoveResult` / `StashRemoval` 都带一个判别字段 `kind`（`removed` / `leftover` / `undo-restored` / `undo-unknown` / `ambiguous-refusal`），公告只按它分支，整条链路上**没有任何对自产文案的 `includes` / 正则判断**（对 `src/ui/` 做了穷尽 grep：所有 `.includes(` / `.match(` / `.test(` 都只剩提交搜索、路径校验、commit hash 校验与 `rebase` todo 行解析，与本次无关）。
- **“未做交叉核对”这句说明以前会被丢掉**：`removeOwnStash` 在 `res.ok || res.gone` 时只返回 `{status: "removed"}`，于是 `stashRemoveBySha` 里精心写好的“删除前的列表未能读取，无法交叉核对是否有其他条目一起消失”被构造出来又扔掉——用户只被告知“已干净删除”。现在该说明作为 `uncrosschecked` 字段带出，同时写进**日志**（`recovery … uncrosschecked=true`）与**弹出提示**（提示用户执行 `git stash list` 自行核对），并且这种结果**不会**再显示“已恢复，插件自己的临时 stash 已删除”那句无条件的成功话术。
- **两个模块对“reflog 损坏”曾给出相反答案**：`worktree` 的前后集合比较把 `git stash list` 退出 0 但无输出当作**空栈**，`pendingRecovery.stashShas` 把同一形状当作**不可读**——同一份字节，两个答案。目前只因调用方恰好先过保守的那一个才没出事，这正是重构后会咬人的隐患。现在只有一个判据 `worktree.readStashList`（`listed` / `empty` / `unreadable` 三态），两个模块都走它，损坏的 reflog 一律 `unreadable`；真正空的栈仍是 `empty`（此时 `refs/stash` 也解析不到，两个信号一致）。
- **重命名折叠会造成 `complete` 误报**：`pendingRecovery.changedPaths` 漏了 `--no-renames`（`worktree.ts` 的 `diffNames` 有），而它是 `complete` 唯一的路径来源。快照暂存一次 `a.txt → b.txt` 的重命名、用户只把目标文件还原进索引时，`--name-only` 只报 `b.txt`，于是 `index` 报 `present`、`complete` 为真、条目被删，而 `a.txt` 的**暂存删除从未回到索引**。`stagedSnapshotInHead` 共用这条路径，同一缺陷会让它在 HEAD 仍含 `a.txt` 时报 `committed: true`。已补上 `--no-renames`，两处一并修好。
- **所有需要读 Git 人类可读输出的调用统一 `LC_ALL=C`**：共享常量 `gitRunner.C_LOCALE`（`ABORT_ENV` 现在是它的别名）。审计结果见 `docs/review` 之外的实现注释：`worktree.ts` 的 `stash push` / `stash drop`、`commitLog.ts` 的 `--shortstat` 兜底都带上了；`pendingRecovery.ts` 与 `worktree.ts` 其余调用全部读 `--format` / `-z` / 退出码这类与语言无关的输出，未依赖文案。
- **自动 stash 的条目无法 `pop`，这是 Git 的行为、不是缺陷**：自动 stash 带 `--include-untracked`，其未跟踪文件被恢复回工作区之后，对同一条目执行 `git stash pop` 必然以 `already exists, no checkout` / `could not restore untracked files from stash` 失败且**条目仍在**（实测）。因此“先 apply 再 pop”永远不会成功，“先 pop 再 apply”则会让每次冲突重试都先做一次破坏性写入。
- **这次顺带修掉一个真实探测缺陷**：`treeBlobs` 解析 `git ls-tree` 时把**第二列**（对象类型 `blob`）当成对象 id，于是未跟踪文件的 blob 比对永远不相等——即使文件就在盘上、内容字节一致，`untracked` 也报 `missing`，`complete` 因此永远为假。这个问题此前被“永不删除”掩盖（`complete` 只用于授权删除），删除恢复后才暴露。修正为取第三列后，`stashPresence` 在标准 autostash 形状下正确给出 `complete: true`。
- 对应新增/改写的用例：`a successful autostash recovery leaves exactly the user's pre-existing entries, by sha`、`a successful append recovery leaves exactly the user's pre-existing entries, by sha`、`a stash pushed between classification and removal is refused and both entries stay`、`a race that lands inside the drop window is undone by git stash store`、`a drop that takes the wrong entry puts it back intact`、`a pop-style conflicting restore keeps the extension's entry and reports it`、`the user's own stashes are never removed in any recovery path`。
- 复审补充的用例（都不需要安装任何 locale，直接构造措辞/形状）：
  - `a clean worktree never records an existing entry as the one the plugin created`：干净工作区上 push 不创建条目，`stashPush` 返回 `undefined`，用户条目未被认领；同一条判据用德文措辞再走一遍纯函数仍是 `undefined`。
  - `a push that raced another one claims no sha at all`：两个新 sha、非零退出、列表读不出来，三种形状都不认领。
  - `a translated drop message does not defeat the rollback`：把德文 `Stash verworfen stash@{1} (…)` 当成 drop 输出，正则解析不了，仅靠删除前后 sha 集合差就把用户条目按精确 sha 复原。
  - `an unreadable drop result is a refusal, not a claimed removal`：自己条目仍在列表、文案无法解析时返回拒绝，不报成功。
  - `a sha already listed twice is a duplicate misdrop from git stash store`：两个槽位指向同一 sha 时拒绝删除，两条都保留，且不再把这个 sha 的槽位名给横幅。
  - `a staged rename restored only at its destination keeps the entry`：先断言 `--name-only` 确实只报 `b.txt`、带 `--no-renames` 才报两个路径；只还原目标后 `index: "missing"`、`complete: false`、结论非 `resolved`、条目保留。
- 第二轮复审补充的用例（对应“自己的 sha 消失不代表只删了自己那条”与两个模块对损坏 reflog 的分歧）：
  - `our sha vanishing is not proof that only our sha vanished`：真实 Git 里先并发删掉插件那条、再让插件的 drop 删掉用户那条，删除后列表为空。旧的 `ok/gone` 判据在这里放行；现在 `dropVerdict` 从“删除前快照里消失的其他 sha”认出受害者，用 `stash store` 复原，断言用户条目按 sha 回到列表。
  - `a drop that cannot be cross-checked says so instead of claiming a clean removal`：没有删除前快照时仍返回 `ok/gone`，但消息必须写出“删除前的列表未能读取、未做交叉核对”，而不是假装核对过。
  - `a drop verdict is decided by identity for every shape the list can take`：纯函数 `dropVerdict` 的十种输入形状（只丢自己 / 双丢 / 普通误删 / 多条同时消失 / 自己仍在 / 列表读不出 / 无快照两种 / 空栈）逐条断言。
  - `a corrupt reflog reads as unreadable, never as an empty stack, in both modules`：删掉 `.git/logs/refs/stash` 造出“`git stash list` 无输出但 `refs/stash` 仍指向条目”的形状，断言 `readStashList` 报 `unreadable`、`pendingRecovery.stashShas` 与 `worktree.stashShasForComparison` **都给 `undefined`**（旧实现一个说空、一个说读不出）；再删掉 `refs/stash` 造出真正空栈，两者都返回 `[]`。
  - `an unreadable stash list is never reported as a missing stash by the restore paths`：造出损坏 reflog 形状后，三条恢复入口（`stashRestoreForAmend`、`stashRestoreWorktreeAfterAmend`、`stashApplyIndexBySha`）都必须返回“无法读取 stash 列表”，而不是 `gone: true`——后者等于告诉用户唯一一份改动没了；并断言 `refs/stash` 在调用后仍指向原 commit，没有任何写入。
- provider 级补充 2 条（`test/recoveryProvider.test.ts`）：`an undone wrong drop is announced as the user's entry being restored, never as our leftover` 断言被复原的条目不会被当成“插件自己的残留条目”并附上 `git stash drop` 命令（那等于让用户删自己的 stash）；`a mixed result reports the leftover and the undo without confusing the two` 断言真正该清理的那条仍按槽位与命令报告。
- 第四轮复审再补（对应“预检读不出”与“公告按文案分类”两处）：
  - `an unreadable reflog at the removal pre-check is a refusal, never a reported removal`：删掉 `.git/logs/refs/stash` 造出损坏形状后直接调用 `stashRemoveBySha`，断言 `refused: true`、`gone: false`、`kind: "refused"`，并断言 `refs/stash` 在调用后**仍指向原 commit**（没有任何写入）。
  - `a removal result carries the shape the announcement needs, not just prose`：断言 `StashRemoval` 在“干净删除”“被拒绝”两种形状下都带 `kind`，并且干净删除**不带** `uncrosschecked`/`message` 这些空字段——公告若退回按文案猜，这条会先红。
  - `an ambiguous refusal is not announced as a restore`（provider 级）：喂一条 `kind: "ambiguous-refusal"` 的结果，断言公告**不**出现“删到了别的条目…已原样恢复”这类宣称，且不出现任何 `git stash drop` 命令。
  - `an unreadable post-drop listing never offers a drop command`（provider 级）：喂 `undo-unknown`，断言公告不给出 `git stash drop stash@{n}`（槽位占用者未知）。
  - `a genuine leftover still offers the drop command`（provider 级）：喂 `kind: "leftover"`，断言仍给出 `git stash drop stash@{0}`——防止上一轮修复把“该给命令”的情况也一起静音。
  - `the no-witness caveat reaches the log and the user, not just the Git module`（provider 级）：喂 `uncrosschecked: true`，断言该说明同时出现在日志行与弹出提示里，且**不**出现无条件的“已恢复…已删除”成功话术。

### 附录 A：字面 pathspec 站点与钉住它的用例

`worktree.ts` 与 `worktreeChanges.ts` 中共有 **9** 个会把 Git 给出的路径回传给 Git 的站点，全部带 `GIT_LITERAL_PATHSPECS`。下表逐点列出覆盖情况；“单独撤掉后”指只从该站点移除环境变量、其余代码与测试不动时的实测结果。

夹具必须让**错 glob 写入的字节与不写不同**，否则用例空转：

- 第 2/3 号：两条路径在快照时都是未跟踪文件，但诱饵在快照**之后**被 `git add`，因此 `restoreUntrackedHalf` 的循环会跳过它；只有 glob 才会把 stash 里的 `DECOY-UNTRACKED` 写到它的工作区与索引上。
  若让诱饵保持未跟踪，它会被自己的那一轮迭代合法恢复成同样的字节，glob 与否无法区分——这正是补测之前该站点为空转的原因。
- 第 4 号：只有目标带快照内的工作区改动，诱饵拿到的是快照**之后**的编辑（`DECOY-NOW`）；glob 会把它回退成 `DECOY-V1`。
  若诱饵的改动发生在快照之前，恢复它就属于正确行为，用例同样空转。
- 第 6/8 号：`restore --worktree` 回退到**索引**里的值，因此诱饵的索引值必须与工作区值不同（先 `git add DECOY-STAGED`、再改成 `DECOY-WT2`）。
- 第 9 号：`restore --staged` 对**新增文件**会整条删掉索引条目；若用“已跟踪文件被回退到 HEAD 值”，那种变化与“没碰它”在内容上无法区分，用例空转。因此两条路径都是新暂存的文件。
