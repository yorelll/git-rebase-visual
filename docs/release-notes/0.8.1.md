## Git Rebase Visual 0.8.1

用于 VS Code 的可视化交互式 Git rebase 扩展：在侧边栏中安全地重排、编辑、锁定和推送 commit，并提供工作区恢复、只读 Diff、AI commit message、stash 与受控 Undo。

> 来源：Git tag `v0.8.1` · GitHub Actions 自动构建 · CI 将执行 `npm run test:release`、VSIX 内容校验与版本记录校验。

### 🐛 修复（0.8.1）

- **“追加到 commit”误报工作区冲突（错误诊断，非数据损坏）**：在 edit 停靠的 rebase 中把暂存内容追加到 commit 后，插件有时会报 `快照中未提交的部分与当前工作区冲突：<文件列表>`，并提示执行 `git stash apply --index`。这是**误判**：被列为冲突的路径当时存放的正是这次追加自己已经提交的内容，并不是用户的新改动，两者并不冲突。
  - **没有丢失任何用户数据**。完整快照（`changeStash`）与 keep-index 残留快照（`unstagedStash`）都仍在 `git stash list` 中，追加本身也已成功（`commit --amend` 与 `rebase --continue` 都正常结束）。真正被跳过的只有“把快照里未提交的部分放回工作区”这一步。
  - **旧提示是个死循环**：提示里建议的 `git stash apply --index` 会重新执行同一段比对，因此得到同一个“冲突”，无论试多少次都不会自行恢复。对这类形状，该提示**不再出现**。
  - **修复方式**：`restoreResidualSnapshot` 比较残留路径时，若工作区内容等于 `stash^2:path`，说明它正是本次追加提交的树内容、自事务开始后无人写过，于是直接放回快照的工作区版本，而不是报冲突。判定完全基于 Git 状态（`git ls-tree` / `git hash-object` 的 blob 比对），不看持久化的 `amended` 标志；只要路径上是任何更晚的内容（与 `stash^2` 不同）就仍然拒绝覆盖。
  - **不变量未变**：插件仍然**永不自动删除 stash**，恢复全程只用 `git stash apply`；也仍然**永不覆盖更新的用户内容**——快照中的“删除”同样保持为冲突，不会以删除文件作为副作用。
  - 新增回归用例：完整复现用户形状（edit 停靠 → `stash apply --index` → `commit --amend --no-edit` → `stash push --keep-index --include-untracked` → `rebase --continue` → 对账），断言残留改动回到工作区、结论不是 `pending`，且两份 stash 都仍在列表里。
- **残留状态探测的误报审计**：复查了 keep-index 快照在日志中出现的 `worktree=missing unstaged=missing` 结论，并用真实 Git 构造两种形状验证：后续 commit 不触碰该路径时，工作区确实缺失、恢复流程会真实写回并报 `restored`；后续 commit 拥有该路径时探测为 `present`、不重复写入；后续 commit 改写该路径时 `rebase --continue` 本身就会冲突，对账不会走到这一步。因此该信号不存在“假 pending / 假 resolved”的形状，已在代码中以注释记录理由。
- **`streamChat` 中途取消用例偶发失败（仅测试）**：该用例原先用固定 5 ms 定时器触发取消，与“客户端读到第一个 delta”竞速——在整轮套件并行、机器负载高时取消可能先于首个数据块解析完成，`chunks` 为空而失败。现在改为在 `onDelta` 首次被调用后立即取消，预置条件不再依赖时序；服务端也改为有上限地继续发送数据，取消若失效会断言失败而不是挂住套件。已实测：把取消路径改成“静默返回”后用例变红（`Missing expected rejection`），恢复后 8/8 通过。

### ✨ 变化（0.8.1）

- **日志改到用户主目录**：会话日志从系统临时目录改为 `<用户主目录>/tmp/log/git-rebase-visual-<version>/`（Linux/macOS 即 `~/tmp/log/git-rebase-visual-0.8.1/`，Windows 为 `C:\Users\<用户>\tmp\log\git-rebase-visual-0.8.1\`）。旧位置 `/tmp/log/...`（Windows `%TEMP%\log\...`）不便于用户自己浏览和附加到问题报告。
  - 版本目录名、每会话一个带时间戳的文件、按大小轮转、保留最近 10 个会话、凭据脱敏与“写入失败只关闭文件日志”的容错行为全部保持不变。
  - **旧日志不迁移、不删除**：0.8.1 之前的日志仍留在原临时目录。每次扩展会话里**第一次**执行 **Git Rebase: Open Logs** 时，会在 **Output → Git Rebase Visual** 追加一行说明，指出旧日志所在位置；只有一行、不弹通知、不重复打扰。

### 🔒 安全与可靠性

- 写操作仍然串行化，恢复流程仍然整轮持有 mutation lock；对账仍然“失败即保守”，任何探测失败都保留记录与 stash。
- 追加路径的自动恢复依旧只写“可证明未被改动过”的路径：工作区内容等于快照本身，或（新增）等于本次追加提交的 `stash^2` 内容。其余情况一律保留记录、横幅与 stash，删除永远由用户自己执行。
- 全量测试扩展至 **217 项**，`npm run typecheck`（src + test）与 `npm run test` 全绿。

### 使用方式

- 下载 `git-rebase-visual-0.8.1.vsix`。
- VS Code：扩展面板 → `...` → **Install from VSIX...**。
- 命令行：`code --install-extension git-rebase-visual-0.8.1.vsix`。

### 功能总览

- 交互式 rebase：拖拽重排、Alt+Arrow 重排、edit/reword/squash/fixup/drop、冲突 Continue/Abort；
- 提交保护：patch-id 锁定、Push guard、`--force-with-lease` 与受控 Undo；
- 工作区辅助：Staged/Changes 文件列表、单文件与批量 stage/restore/unstage、VS Code 左右 Diff、auto-stash 与 stash list；
- AI message：流式生成、deadline、取消、trailer 保留与 staged-only commit；
- 诊断与质量：OutputChannel、带轮转与脱敏的会话日志、可解释的写锁与看门狗恢复、真实 Git 集成测试、webview DOM 回归、VSIX 内容门禁。
